# RAG Knowledge Assistant

Ask questions about your own documents. Answers are generated by a pluggable LLM, grounded in the
retrieved passages, and carry numbered citations (document, version, page).

This README describes what is implemented and tested today. See [Limitations](#limitations) for what is not.

## How it works

```
upload / sample_docs  ->  Loader (txt, md, pdf, docx, csv)  ->  Chunking (sentence | recursive | structure)
                                                                      |
                              SQL (documents, versions, chunks)  <----+---->  Embeddings (sentence-transformers)
                                        |                                              |
                                        |                                       Vector store (Chroma | pgvector)
                                        v                                              |
Question -> (rewrite follow-ups) -> Hybrid retrieval: vector + BM25 keyword -> RRF fusion -> optional reranker
                                        |
                                        v
                    Relevance gate -> Context builder -> LLM (Groq | OpenAI | Claude | Ollama | compatible)
                                        |
                                        v
                         Answer with validated [1] [2] citations, stored in the conversation
```

* **SQL is the system of record** (SQLite by default, PostgreSQL possible): documents, versions, chunks,
  conversations, settings. The vector index can always be rebuilt from it.
* **Versioning:** uploading a changed file with the same name creates a new version; the switch happens
  in one database transaction, so answers never mix old and new text. Identical content is a no-op;
  the same content under another name is rejected (409).
* **Grounding:** the LLM is only called when at least one passage passes the relevance gate. Otherwise the
  answer is "not found in the documents". Retrieved text is treated as data, never as instructions.
* **Citations:** every `[n]` in an answer is checked against the passages that were actually given to the
  model; invented numbers are removed. (Whether a passage truly *supports* a claim is not checked.)

## Quick start

```bash
python -m pip install -r requirements.txt
python -m uvicorn main:app --port 8000
```

Open http://localhost:8000. On the first start the files in `sample_docs/` are indexed once; after that
everything is read from `data/` (SQLite database, uploaded originals, Chroma index) and start-up is fast.
Copy `.env.example` to `.env` to change settings. Every setting is documented there.

LLM: install [Ollama](https://ollama.com) and pull a model (for example `ollama pull llama3.1`) for a local,
key-free setup, or put `GROQ_API_KEY`, `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` in `.env`. Keys are read
from the environment only; they are never stored in the database or returned by the API.

## Web UI

Open http://localhost:8000. One chat-centred page:

* **Chat** (main area): streamed answers with clickable `[1]` citation chips. Each answer has a collapsible **Sources** panel (document, version, page, match score and the quoted passage). Follow-up questions keep the conversation. **Send** becomes **Stop** while an answer is running; a stopped turn is not saved. Use of the fallback provider, a failed query rewrite and "nothing relevant found" are shown explicitly. The message log scrolls on its own and the question box stays pinned at the bottom.
* **Developer view** (toggle in the header, remembered per browser): adds the retrieved-but-not-cited passages to each Sources panel, plus keyword coverage, rerank score, chunk id and token usage. Off by default, so end users never see raw retrieval output.
* **Conversations** (sidebar): every past conversation, newest first, with its first question as the title and a message count. Click to reopen it with its citations, **New** to start another, **x** to delete one. The server stores them, so they survive reloads and restarts.
* **Model** (sidebar): choose provider and model, **Test** the connection, **Save**. Providers without an API key are disabled.
* **Documents** (sidebar): a table with name, version, chunk count and a status pill (ready, stale, indexing, failed). **Details** shows every version (status, chunks, chunking strategy, reason, size); **Re-index** and **Delete** act on one document. **Add a document** is a two-step flow (1. select a file, 2. upload and index) with a real upload progress bar and the server's error message when something is rejected.

Uploads accept `.txt`, `.md`, `.pdf`, `.docx` and `.csv`. All server and model text is inserted as plain text, never as HTML. The old retrieval-only "Search chunks" tab was removed from the UI; the `POST /api/query` endpoint still exists for API users.

## Supported documents

| Format | How it is read |
|---|---|
| `.txt`, `.md` | UTF-8 text (BOM accepted) |
| `.pdf` | Text layer, page by page (page numbers are kept for citations). No OCR; encrypted or scanned PDFs are rejected with a clear message |
| `.docx` | Paragraphs, headings (as Markdown headings) and tables (as Markdown tables) |
| `.csv` | Each row becomes one sentence: `Header: value; Header: value.` |

Maximum upload size is 5 MB by default (`MAX_UPLOAD_BYTES`). Filenames are validated; path traversal is rejected.

## Chunking

Set `CHUNK_STRATEGY` (and `CHUNK_SIZE`, `CHUNK_OVERLAP`) in `.env`.

| Strategy | What it does |
|---|---|
| `sentence` (default) | The original behaviour: split at Markdown headings, then pack whole sentences up to `CHUNK_SIZE`. Overlap is only used when a single sentence is longer than `CHUNK_SIZE`. |
| `recursive` | Split at headings, then use the coarsest separator that works (blank line, line, sentence, word, character) and merge pieces back up to `CHUNK_SIZE` with **real overlap** between neighbouring chunks. Text is cut at a finer level only when it does not fit. |
| `structure` | `recursive` for prose. Markdown/DOCX tables are split by row with the **header repeated in every chunk**; CSV records are never cut (an oversized record is split at field boundaries and keeps its first field). |

Chunks never cross a Markdown heading in any strategy. Each document version records the strategy, size
and overlap it was built with. After changing them, existing documents show `chunking_outdated: true`
until you call `POST /api/v1/documents/reindex` (this rebuilds from the stored originals).

Measured on small synthetic sets with the real embedding model (hybrid retrieval, top 3, "all facts
needed for the answer are inside one retrieved chunk"):

| Test | sentence | recursive | structure |
|---|---|---|---|
| 30-row Markdown table, 8 questions needing a row and its column header | 2/8 | 2/8 | **8/8** |
| Prose where each answer spans two adjacent sentences, overlap = `CHUNK_SIZE`/3, chunk sizes 200 to 400 | 85/120 | **120/120** | not tested |
| The same prose with the default overlap of 50 | 85/120 | 84/120 | not tested |
| CSV with wide records, 8 questions | 7/8 | 7/8 | 7/8 |

Take-aways: use `structure` if you upload tables. Use `recursive` with an overlap of about one third of the
chunk size (for example `CHUNK_SIZE=300`, `CHUNK_OVERLAP=100`) for prose; with a small overlap (shorter than a
sentence) it behaves like `sentence`. These sets are small and synthetic, so treat them as evidence that the
mechanisms work, not as a benchmark of your own documents.

## Retrieval quality

| Setting | Meaning |
|---|---|
| `RAG_RETRIEVAL_MODE=hybrid` (default) | Vector search plus BM25 keyword search, merged with reciprocal rank fusion. Finds exact codes, names and numbers that embeddings blur. `vector` restores embeddings-only search. |
| `RAG_LEXICAL_MIN_COVERAGE=0.6` | A passage below `RAG_MIN_SCORE` is still used when it contains at least this share of the question's keyword weight. |
| `RAG_RERANKER=cross-encoder` | Optional cross-encoder reorders the candidates (about 90 MB model downloaded on first use; roughly 0.3 to 0.5 s per query on CPU). Off by default. If it fails the answer still returns, with a `rerank_failed` warning. |

Measured on 8 questions about near-identical error codes (`ERR-1021`, ...): vector only found the right
passage first 2 times, hybrid 6 times, hybrid with the reranker 8 times. On ordinary questions all modes scored
the same (8/8).

## API

Interactive docs: http://localhost:8000/docs

| Method and path | Purpose |
|---|---|
| `POST /api/v1/chat` | Ask a question. JSON, or Server-Sent Events with `"stream": true` (`retrieval`, `start`, `token`, `done`, `error`). Body: `question`, optional `conversation_id`, `top_k`, `min_score`, `rewrite`, `provider`, `model` |
| `GET /api/v1/conversations` | List conversations (newest first; title, message count, timestamps; no message bodies; empty ones omitted) |
| `GET` / `DELETE /api/v1/conversations/{id}` | Read or delete a conversation |
| `POST /api/v1/documents` | Upload (multipart `file`). 201 created or updated, 200 unchanged, 409 duplicate content |
| `GET /api/v1/documents`, `/{id}`, `/{id}/versions` | List, detail, version history |
| `DELETE /api/v1/documents/{id}` | Delete the document, its versions, vectors and files |
| `POST /api/v1/documents/{id}/reindex`, `POST /api/v1/documents/reindex` | Rebuild one or all documents from the stored originals |
| `GET /api/v1/index/status` | Consistency report: database versus vector index |
| `GET /api/v1/llm/providers`, `/providers/{name}/models`, `POST /providers/{name}/test` | Provider discovery and health check |
| `GET` / `PUT /api/v1/llm/config`, `POST /api/v1/llm/config/reset` | Active provider, model, temperature, fallback (persisted, never contains keys) |
| `POST /api/v1/llm/complete` | Plain completion without retrieval (JSON or SSE) |
| `POST /api/query`, `GET /api/documents`, `GET /api/status`, `POST /api/upload`, `DELETE /api/documents/{filename}` | Original endpoints with their original response shapes, kept for compatibility. The UI still polls `GET /api/documents` for its document table; everything else it calls is under `/api/v1` |

If the chosen provider fails, a configured fallback provider is used only when you enabled it, and the
response says so (`used_fallback`, `fallback_from`, `fallback_reason`). It is never silent.

## Operations

| Feature | Details |
|---|---|
| Request ids | Every response has `X-Request-ID` (a valid id sent by the caller is kept, anything else is replaced). Every log line and error body carries it. |
| Access log | One line per request: method, path (no query string), route template, status, duration, client. Health and metrics calls are not logged. |
| Metrics | `GET /metrics` (Prometheus text): request count and latency histogram by route template, rate-limit rejections, unhandled errors, plus gauges for documents, searchable vectors, orphan vectors and index consistency. No question or document text is ever in a metric. Disable with `METRICS_ENABLED=false`. |
| Health | `GET /health/live` (process is up) and `GET /health/ready` (200 once the knowledge base is usable, 503 otherwise). |
| Rate limiting | Sliding window per client address: `RATE_LIMIT_LLM_PER_MINUTE` (chat, completions, search, connection tests) and `RATE_LIMIT_WRITE_PER_MINUTE` (uploads, deletes, re-index, config changes), default 30 each. Over the limit: HTTP 429 with `Retry-After`. Reads, status polling, static files and health checks are never limited. `X-Forwarded-For` is only trusted with `TRUST_PROXY_HEADERS=true`. Limits are per process and per address: protection against loops and one noisy client, not against a distributed attack. |

## Evaluation

```bash
python -m app.evaluation                              # retrieval metrics on eval/golden.jsonl
python -m app.evaluation --mode vector,hybrid         # compare settings side by side
python -m app.evaluation --reranker cross-encoder --chunk-strategy recursive --chunk-overlap 100
python -m app.evaluation --generate                   # also run the real LLM pipeline (slow)
python -m app.evaluation --min-context-hit 0.9        # exit code 1 below a threshold (quality gate)
```

The corpus (`sample_docs/` by default) is indexed into a temporary directory, so runs are reproducible and your real data is untouched. Add your own questions to `eval/golden.jsonl` (one JSON object per line: `question`, `expected_sources`, optional `expected_facts`, or `"should_answer": false`). Metrics: `source_hit_at_1`, `source_hit_at_k`, `mrr`, `context_hit` (an expected source survives the relevance gate), `fact_recall`, `refusal_ok`, and with `--generate`: `answer_has_facts`, `cited_expected_source`, `answer_refusal_ok`. Fact checks are case-insensitive substring matches, which are strict: a correct answer worded differently counts as a miss.

Current result on the shipped set (21 questions over the sample documents): every answerable question is retrieved first and its facts are in the context, in both `vector` and `hybrid` mode. One of three off-topic questions ("What will the company profit be in 2030?") still passes the relevance gate, because the profit document is about the right topic; the LLM is what declines it. The shipped set is small and easy, so treat it as a regression guard, not a benchmark.

## Docker

```bash
cp .env.example .env                          # set API keys / options
docker compose up --build                     # app on http://localhost:8000, data in the rag-data volume
docker compose --profile ollama up --build    # also run a local Ollama (then: docker compose exec ollama ollama pull llama3.1)
```

* The image bakes in the embedding model, runs as a non-root user and works without internet access (`HF_HUB_OFFLINE=1`). Set `HF_HUB_OFFLINE=0` if you enable `RAG_RERANKER=cross-encoder`, whose model is downloaded on first use. The image is about 3 GB (PyTorch, ChromaDB and the embedding model).
* A health check calls `/health/ready`. Start-up took about 15 seconds in my test.
* Inside the container, `OLLAMA_BASE_URL` defaults to `http://host.docker.internal:11434` (an Ollama running on your machine). Set it to `http://ollama:11434` when you use the `ollama` profile.
* PostgreSQL: `POSTGRES_PASSWORD=... docker compose --profile postgres up --build postgres app-postgres` stores metadata and vectors in PostgreSQL + pgvector instead of SQLite + Chroma. The `app` and `app-postgres` services both publish port 8000, so run only one of them.
* Run it behind your own reverse proxy with TLS for anything beyond local use; there is no authentication.

## Tests

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests -q
```

Latest full run: 590 passed with the `integration` tests included, plus the 21 pgvector contract tests (skipped without a database) passing against PostgreSQL 16 with pgvector, 0 failures.

The suite uses a temporary SQLite database, a real Chroma index in a temporary folder, a fake embedder and
mocked LLM providers, so it needs no network. Tests that load the real embedding model are marked
`integration` (`-m "integration or not integration"` runs them). The pgvector contract tests run only when
`RAG_TEST_PGVECTOR_URL` points at a PostgreSQL database with the pgvector extension, for example one started with `docker run -d -e POSTGRES_PASSWORD=testpass -e POSTGRES_DB=ragtest -p 55432:5432 pgvector/pgvector:pg16` and `RAG_TEST_PGVECTOR_URL=postgresql+psycopg://postgres:testpass@127.0.0.1:55432/ragtest` (needs `requirements-postgres.txt`).

## Limitations

* **Cloud LLM providers (Groq, OpenAI, Claude) are tested against mocks only**; no real API keys were used. Ollama was tested live.
* **pgvector** passed all 21 shared contract tests and a full ingest-and-retrieve run (same evaluation scores as Chroma) against PostgreSQL 16 with pgvector. Not tested: very large collections (no approximate-nearest-neighbour index is created, so search is an exact scan), other PostgreSQL versions, or the `postgres` compose profile end to end (its configuration was only validated).
* **No authentication or multi-tenancy.** Anyone who can reach the port can read, upload and delete documents. Do not expose this service publicly. Rate limits and metrics are in-process and per instance.
* **No Alembic migrations.** Tables are created automatically, and missing columns are added in place by a small
  upgrade step; anything more complex needs real migrations.
* **Ingestion is synchronous**: an upload request waits until the document is indexed.
* **No OCR**, so scanned PDFs cannot be read. DOCX and CSV have no page numbers.
* The keyword index is held in memory (fine for thousands of chunks, not millions).
* Citation validity is checked, citation *support* is not.
* The UI shows per-document version history, but there is no way to roll back to an older version from it. Conversations cannot be renamed or searched.
* The UI was exercised in headless Chrome only (scripted DevTools checks: 21 for the chat, conversation list and document table, 9 for layout and input focus); Firefox, Safari and screen readers were not tested. Basics such as labels, roles, focus outlines, live regions, keyboard-operable controls and reduced motion are in place, but full accessibility compliance needs manual testing with assistive technologies.
* If you delete every document, the next start treats the empty database as a first run and re-indexes `sample_docs/`.
* Local CPU-only LLMs are slow (25 to 60 s per answer with `llama3.1`).
* After changing the embedding model, documents are marked `stale` and only partly searchable until reindexed.
* `faiss-cpu` stays in `requirements.txt` only for the unused legacy `rag_engine.py`.
